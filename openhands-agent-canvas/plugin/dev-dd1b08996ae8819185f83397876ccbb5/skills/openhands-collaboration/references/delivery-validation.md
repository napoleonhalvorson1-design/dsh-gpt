# 指定交付检查与定点修复（5.26）

按实际需求选择一条最终检查命令，配置在项目或单次运行的 `deliveryValidation`。未配置的项目保持原流程。它不是固定验收阶段，不另开审查 AI。

```json
{
  "deliveryValidation": {
    "command": "node scripts/test-app.mjs",
    "timeoutSeconds": 60,
    "autoRepair": true
  }
}
```

MCP：`canvas_save_project` 的 `state`（包括 `preset:"five-ai"`）保留此设置；`canvas_start_run` 可单次覆盖。CLI：`canvas runs start --project ID --validation-file check.json`，文件内容为上面内层的检查对象。单次覆盖不改已保存项目。固定流程可用 `autoRepair:false`；自动修复需要该运行已有的已验证强规划负责人。需要 S3 和自托管执行入口。

检查在全部实现结束后执行，使用完整、经 SHA-256 校验并已入桶的成果，在独立目录中运行。单叶交付复用已有不可变快照，避免重复上传；多叶汇合先保存完整合并快照。目录只包含归档文件，需要的依赖准备应包含在命令中，例如 `npm ci && npm test`，整个命令计入 5–300 秒的预算。命令可生成临时文件，交付及修复基线仍为检查前固定的源码快照。

确认命令以 0 退出才可成功交付。实际非零退出或确认终止的超时，才把具体错误交给原已验证强负责人修复一次；模型、深度、用户设置及 DeepSeek 锁保留。修复继承原完整成果、使用新隔离目录，无额外审查，最后自动重跑同一检查。第二次失败停止；明确继续可再做一次定点修复，已完成阶段不重跑。每次修复有预算，修复阶段不另设自动后备。没有最终通过检查的成果及已被明确拒绝的单叶成果，不混入成功耗时样本。

`run.deliveryCheck` 保存冻结策略、`current`、`attempts`、`repairCount` 和 `autoRepairCount`。每次检查绑定源代码 SHA、命令 SHA、唯一请求 ID。原生回执先保留执行身份再派发，完成后持久化退出码；确认通过的回执跨恢复复用。控制器重启、响应丢失和桶错误不重跑原模型或已完成命令。回执缺失或结果不确定时停止核对，不能把连接故障当作软件失败来调用修复 AI。取消等待原生检查确认结束，之后不会自动修复；明确继续已取消的检查使用新检查身份。

一次真实任务曾在缺陷检查与修复之间等待 209 秒，见自有仓库 `.openhands/benchmarks/real-speed-5.25.json`。新逻辑去掉这段手工衔接，但真实项目整体提速仍须测量，不能据此宣称整体 11 倍。

验证包括原生 Python 子进程的去重、确认失败、超时和取消，以及真实 HTTP/签名 S3 夹具的强模型修复、快照继承、第二次失败、明确继续、控制器重启、丢失回执及存储恢复。上海、硅谷、首尔均已用 `/usr/bin/true` 验证原生命令和持久化回执；没有模型推理，这项探针不证明项目检查或修复已实测。
